这份官方文档详细说明了 OneNET 平台的 **HTTP 全局推送（数据流转）** 功能。

简单来说，它的核心逻辑就是：**让 OneNET 平台作为客户端，把你之前搭建的 Spring Boot 后端当作服务器** 。当你的硬件设备把数据发给 OneNET 后，OneNET 会立刻通过 HTTP 请求，主动把数据“塞”给你的 Spring Boot 接口，这就是典型的 Webhook 机制。

为了让你在写代码时思路清晰，我把这份文档拆解为**三个核心开发阶段**和**一个避坑指南**：

### 1. 握手认证阶段（URL 验证）

当你在 OneNET 后台配置好你的 Spring Boot 接口 URL 并点击“提交”时，OneNET 会先试探一下你的接口是不是真的存在且合法。

*
**请求方式：** OneNET 会向你的 URL 发送一个 `GET` 请求 。


*
**携带参数：** URL 会拼接三个参数：`msg`（随机字符串）、`nonce`（随机字符串）、`signature`（加密签名） 。


* **你的后端需要做什么：**
*
**正规做法：** 拿到自己设置的 `token`，加上 `nonce` 和 `msg` 拼接成字符串，经过 MD5 加密和 Base64 转换后，跟 OneNET 传来的 `signature` 对比，一致则原样返回 `msg` 的值 。


*
**偷懒做法（文档允许）：** 如果你不想写复杂的加密校验，可以在 Spring Boot 接口里直接提取请求里的 `msg` 参数，然后原样返回（Return 即可），同样能通过验证 。





### 2. 核心接收阶段（数据推送）

握手成功后，OneNET 就会源源不断地把设备数据推过来了。

*
**请求方式：** 这次变成了 `POST` 请求 。


*
**数据格式：** 数据会被放在 HTTP 请求的 Body 中，格式是 JSON 。


*
**包含字段：** 最核心的是 `msg` 字段（你的设备真实数据就在这里面，如果是安全模式则是一串 AES 密文），另外还有用来防重复的 `id` 和时间戳 `time` 等 。


*
**你的后端需要做什么：** 必须在收到数据后，向 OneNET 返回 **HTTP 200** 状态码，表示“我收到了” 。



### 3. 平台惩罚机制（重推与关停）

这部分是文档中最严厉的规则，直接关系到你的服务稳定性：

*
**3 秒生死线：** 你的 Spring Boot 接口必须在收到数据的 **3 秒内**返回响应 。超时或者没返回 HTTP 200，OneNET 会判定发送失败 。


*
**指数重试：** 失败后，OneNET 会不断重试（间隔 1秒、5秒、10秒...最长 1 小时） 。


*
**封号警告：** 如果连续失败达到 500 次，或者每小时超时 500 次，你会收到告警短信 。如果连续失败达到 2000 次，或者每小时超时 1000 次，OneNET 会直接**关停你的推送服务** 。



---

### 💡 给你的 Spring Boot 架构建议（必看避坑指南）

基于文档第 5 页的建议，如果你打算在目前的 Spring Boot 项目里接入这个服务，**绝对不能在 Controller 里直接处理业务逻辑然后再返回**。

**正确的架构应该是（异步处理）：**

1. 你的 Controller 接收到 OneNET 的 POST 请求 。


2. 把收到的 JSON 数据立刻扔进本地缓存、消息队列（或者开启一个新线程） 。


3. 也就是在 1 毫秒内，Controller 直接 `return "success"` (对应 HTTP 200)，把 OneNET 打发走，防止它判定你超时 。


4. 然后你的系统在后台慢慢解析数据并存入 MySQL 。


5. 为防止 OneNET 服务器的请求被拦截，建议把 `183.230.40.0/24`、`183.230.102.0/24` 和 `218.201.45.0/25` 加进白名单 。
