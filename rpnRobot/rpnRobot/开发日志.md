开发日志
======

> 本文用于持续记录后端与 OneNET 云平台集成、数据推送与入库等相关开发工作，方便后续排查问题与功能扩展。

2026-02-24 OneNET 数据推送接入（第一版）
----------------------------------

**一、配置层改动**

- 在 `application.yml` 中新增 `onenet` 相关配置，用于统一管理 OneNET HTTP 推送的安全参数：

  - `onenet.token`：在 OneNET 控制台「数据流转 → 数据推送」配置的 Token，参与 URL 验证与消息签名校验。
  - `onenet.aes-key`：当选择“安全模式（AES 加密）”时使用，存放 OneNET 生成的 Base64 编码 AES 密钥（目前仅预留，尚未启用解密逻辑）。

**二、工具与基础设施**

- 新增 `util.OneNetUtils`：
  - 提供签名校验方法 `checkSignature(token, msg, nonce, signature)`。
  - 根据开发指南实现签名算法：`A = token + nonce + msg` → `MD5(A)` → `Base64` → `URLDecode`，再与请求中的 `signature` 比对。

- 新增消息存储实体 `pojos.DeviceMessage`：
  - 字段：`id`, `msg`, `nonce`, `signature`, `pushTime`, `messageId`。
  - 用于原样保存 OneNET 推送中的关键字段，便于后续排查、重复消息过滤与业务二次解析。

- 数据持久化层：
  - 新增 `DeviceMessageMapper`（MyBatis 注解版 Mapper）：
    - 提供 `insert(DeviceMessage deviceMessage)` 方法，将一条推送消息写入 `device_message` 表。
  - 新增服务接口 `DeviceMessageService` 及实现 `DeviceMessageServiceImpl`：
    - 对外暴露 `save(DeviceMessage deviceMessage)`，当前实现为同步入库，后续可在此处扩展异步写库、消息队列等能力。

**三、OneNET 回调接口实现**

- 新增 `OneNetCallbackController`，统一处理 OneNET HTTP 推送回调：

  1. **URL 验证（GET /onenet/callback）**
     - 从 QueryString 中接收 `msg`, `nonce`, `signature`。
     - 使用 `OneNetUtils.checkSignature` 校验签名：
       - 校验失败：返回 HTTP 403 + `"invalid signature"`。
       - 校验成功：原样返回 `msg`，符合 OneNET URL 验证规范。

  2. **数据推送接收（POST /onenet/callback）**
     - 请求体为 JSON，字段包括：`msg`, `signature`, `nonce`, `time`, `id`。
     - 步骤：
       - 使用同一套签名校验逻辑校验请求来源。
       - 将收到的数据封装为 `DeviceMessage` 实例并调用 `DeviceMessageService.save` 写入数据库。
       - 尽快返回 HTTP 200（响应内容 `"success"` 或 `"signature invalid"`），避免 OneNET 判定超时并触发指数退避重试。
     - 当前版本仅保存原始 `msg` 字段，不对其中业务 JSON 作进一步解析，后续可根据具体业务格式扩展。

**四、安全与过滤器调整**

- 修改 `TokenFilter` 过滤器逻辑：
  - 原逻辑仅对 `/login` 请求放行，其余路径要求携带 JWT Token。
  - 新增对 `/onenet/callback` 的放行规则，使来自 OneNET 云平台的 HTTP 回调请求无需前端登录态即可被接受并处理。
  - 确保不会因安全过滤导致 OneNET 推送全量失败（从而触发告警或推送关停策略）。

**五、数据库准备建议**

- 建议在 `cpnrobot` 数据库中创建 `device_message` 表用于存储推送记录，示例 SQL 如下（需手动在 MySQL 中执行）：

  ```sql
  CREATE TABLE device_message (
      id INT PRIMARY KEY AUTO_INCREMENT,
      msg TEXT,
      nonce VARCHAR(32),
      signature VARCHAR(128),
      push_time BIGINT,
      message_id VARCHAR(64)
  );
  ```

**六、后续规划（待选）**

- 基于 `msg` 字段的实际 JSON 格式：
  - 解析设备上报的数据内容，拆分到更细粒度的业务表（如设备状态、传感器数据、告警日志等）。
  - 实现重复消息过滤（基于 `message_id`）和重放检测。
- 支持 OneNET “安全模式”：
  - 衔接开发指南中的 AES 解密逻辑，使用 `onenet.aes-key` 对密文 `msg` 进行解密还原。

2026-02-24 调试日志增强（控制台输出）
--------------------------------

**一、OneNET 回调链路调试信息**

- 在 `OneNetCallbackController` 中增加详细控制台输出，覆盖以下关键节点：

  1. **URL 验证（GET /onenet/callback）**
     - 打印收到的请求参数：`msg`、`nonce`、`signature` 和当前使用的 `token`。
     - 打印签名校验结果：
       - 校验失败：输出“签名校验失败，拒绝本次 URL 验证请求”，并返回 403。
       - 校验成功：输出“签名校验通过，原样返回 msg，URL 验证成功”，并返回原始 `msg`。

  2. **数据推送（POST /onenet/callback）**
     - 收到请求时，打印完整的推送体字段：`msg`、`nonce`、`signature`、`time`、`id`。
     - 签名校验失败时：
       - 控制台输出“签名校验失败，本次数据将不会入库，但仍返回 200 避免平台长时间重试”。
     - 签名校验成功时：
       - 打印准备写入数据库的 `DeviceMessage` 对象字段明细（msg、nonce、signature、pushTime、messageId）。
       - 在调用 `DeviceMessageService.save` 前后分别输出“准备将数据写入 device_message 表”与“已调用 DeviceMessageService 保存数据，向 OneNET 返回 success”，用于确认入库流程是否按预期执行。

**二、数据入库层调试信息**

- 在 `DeviceMessageServiceImpl.save` 中增加入库日志：
  - 调用前打印“开始写入 device_message 表”以及将要写入的 `DeviceMessage` 所有字段值。
  - 调用 `deviceMessageMapper.insert` 之后，打印“device_message 表写入完成（insert 已执行）”，用于确认 Mapper 已成功执行。

**三、过滤器请求链路调试信息**

- 在 `TokenFilter` 中增强请求与鉴权相关的控制台输出：
  - 每次请求进入过滤器时，打印当前请求的 `URI`。
  - 当请求为登录或 OneNET 回调时，打印“放行请求（登录或 OneNET 回调）”及对应 `URI`。
  - 对需要鉴权的接口：
    - 打印从请求头中获取到的 `token` 值。
    - 当未获取到 `token` 时，打印“未获取到 token，返回 401 未登录”。
    - 当 `token` 解析成功时，打印“token 校验通过，当前用户 id=xxx”。
    - 当解析失败抛出异常时，打印“token 校验失败，返回 401”以及异常信息。
  - 在最终放行请求前，打印“已通过校验，放行后续过滤器与业务逻辑”，便于追踪请求完整流转过程。

2026-02-24 设备数据同步到 zzulicloud
---------------------------------

**一、zzulicloud 数据源配置**

- 在 `application.yml` 中新增 `zzulicloud.datasource` 段，用于连接已有的 MySQL 数据库 `zzulicloud`：

  - `zzulicloud.datasource.url`：默认假设为 `jdbc:mysql://localhost:3306/zzulicloud?...`，与 `cpnrobot` 同实例，仅数据库名不同。
  - `zzulicloud.datasource.username` / `password`：默认与当前项目 MySQL 账号一致（`root` / `1887418187M`），如有调整可在此处修改。

**二、zzulicloud 目标表设计**

- 为避免与原有历史数据产生冲突，在 `zzulicloud` 数据库中新增专用表 `onenet_device_message`，用于存储从当前后端同步过去的设备推送数据。
- 建议建表 SQL 如下（需在 `zzulicloud` 数据库中执行）：

  ```sql
  CREATE TABLE onenet_device_message (
      id INT PRIMARY KEY AUTO_INCREMENT,
      msg TEXT,
      nonce VARCHAR(32),
      signature VARCHAR(128),
      push_time BIGINT,
      message_id VARCHAR(64)
  );
  ```

**三、zzulicloud 同步实现**

- 新增仓库类 `ZzulicloudDeviceMessageRepository`（基于简单 JDBC 实现）：

  - 通过 `@Value` 读取 `zzulicloud.datasource.url/username/password`。
  - 使用 `DriverManager.getConnection` 与 `PreparedStatement` 直接连接 zzulicloud 数据库。
  - 提供方法 `insert(DeviceMessage deviceMessage)`，执行：

    ```sql
    INSERT INTO onenet_device_message(msg, nonce, signature, push_time, message_id)
    VALUES(?, ?, ?, ?, ?)
    ```

  - 控制台输出：
    - 写入前：打印目标 URL 及将要写入的字段值。
    - 写入成功：打印受影响行数。
    - 写入异常：打印异常信息（不影响主库 cpnrobot 的写入）。

**四、业务服务层同步逻辑**

- 在 `DeviceMessageServiceImpl` 中注入 `ZzulicloudDeviceMessageRepository`：

  - 保持原有对 `cpnrobot` 中 `device_message` 表的写入逻辑不变。
  - 在主库写入成功后，增加同步步骤：
    - 输出“开始同步写入 zzulicloud.onenet_device_message 表”。
    - 调用 `zzulicloudDeviceMessageRepository.insert(deviceMessage)`。
    - 输出“同步写入 zzulicloud.onenet_device_message 逻辑执行结束”，配合仓库内部日志，可完整观察 zzulicloud 写入流程。
