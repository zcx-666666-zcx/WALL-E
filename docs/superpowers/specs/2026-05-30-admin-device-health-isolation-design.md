# 后台设备、远程监控、健康数据与用户隔离设计

## 目标

把 WALL-E 后台管理系统整理成一个能稳定演示、同时具备基础数据隔离的版本：

- 每个用户默认拥有一台 WALL-E 设备。
- 默认设备名称为 `瓦力`。
- 默认设备号为 `WALLE_1`。
- 硬件端统一使用 `DEV_NAME = "WALLE_1"`。
- 提供一个 Python 演示脚本，用来模拟硬件端发送健康数据。
- 用户数据隔离以登录 token 中的用户身份为准，不能再依赖前端传来的 `userId`。

## 范围

这次做的是第一版正式隔离和演示能力，不做完整 UI 重构。

本次包含：

- 默认设备自动创建和保护。
- 设备相关流程按登录用户隔离。
- 健康数据模拟脚本。
- 远程监控固定房间逻辑整理。
- 后台页面只做必要修正，保证设备、健康、监控页面演示稳定。

本次不包含：

- 多设备多房间的完整远程监控模型。
- 后台管理页面整体视觉重做。
- 重建健康数据表结构。
- 猜测或重生成 OneNET 生产凭证。

## 当前发现

硬件端 `Hardware-pi/config.py` 里现在写的是 `WALEE_1`，这是拼写错误，应该改为 `WALLE_1`。

硬件端 Socket.IO 控制器会加入 `robot_{DEV_NAME}` 房间。修正后，控制指令应发送到 `robot_WALLE_1`。

远程监控页面显示了房间号输入框，默认值是 `0001`，但代码里多处也写死了 `0001`。第一版应该明确把它做成固定演示房间，而不是看起来可编辑、实际不可编辑。

健康监测页面当前默认 `deviceId` 和这次要统一的默认设备不一致，应该默认使用 `WALLE_1`。

后端有多个接口接收前端传入的 `userId`。这不是可靠隔离边界，因为客户端可以伪造别人的用户 ID。后续改到的流程都应改成使用 JWT 中的当前用户 ID。

## 推荐架构

默认设备由后端兜底，前端只展示结果。

当登录用户请求设备列表时，后端先确保该用户存在默认设备：

- `machines = "瓦力"`
- `connectionId = "WALLE_1"`
- `robot_ip = system_config["robot.default-ip"]`，没有配置时使用空值或当前默认值
- `user_id = 当前登录用户 ID`

然后后端把这台设备作为普通设备列表的一部分返回。前端不需要自己在页面里硬塞默认设备。

## 后端改动

### 设备管理

在现有 `contract_machine` 流程中加入默认设备兜底逻辑。

行为要求：

- `GET /api/contractMachine/search/{userId}` 不再信任路径里的 `userId`，实际使用 `CurrentHolder.getCurrentId()`。
- 返回设备列表前，检查当前用户是否有 `connectionId = "WALLE_1"` 的设备。
- 如果不存在，则自动插入默认设备。
- 如果已存在但显示名不同，除非显示名为空，否则不强行覆盖用户已有名称。
- 默认设备不允许普通删除接口删掉。
- 默认设备仍允许修改机器人 IP。

前端这一版可以继续调用原接口，但安全边界必须由后端控制。

### 用户数据隔离

本次触碰到的后端接口应使用 `CurrentHolder.getCurrentId()` 判断数据归属，不再相信请求体或路径里的用户 ID。

最低完成范围：

- 设备列表、添加、删除、修改 IP。
- 如果验证流程会用到事件页面，则同步隔离事件列表和写操作。
- 如果验证流程会用到联系人页面，则同步隔离联系人列表和写操作。
- 机器人控制接口必须确认传入的 `machineId` 属于当前登录用户，再发送控制命令。

这样先堵住演示和后台管理中最直接的数据串号问题。

### 健康数据

继续沿用现有健康数据接收接口：

- `POST /api/healthy/addRate`
- `POST /api/healthy/addHumidity`
- `POST /api/healthy/addBreathe`
- `POST /api/healthy/addTemperature`
- `POST /api/healthy/addFall`

模拟脚本发送 `deviceId = "WALLE_1"` 和当前毫秒时间戳。现有查询接口继续按 `deviceId` 查询，健康页面直接读取模拟数据。

## 硬件端改动

修改 `Hardware-pi/config.py`：

- `DEV_NAME = "WALLE_1"`
- `TOPIC_PUB` 中的设备名同步改为 `WALLE_1`。
- 如果 token 资源字符串里直接写死了设备名，也需要检查并修正；但不能凭空生成新 token。

除设备名拼写外，不改其他硬件行为。

## 远程监控

这一版保留 WebRTC 房间 `0001` 作为固定演示房间。

页面上应把房间号表现为固定状态，而不是普通可编辑输入框。代码里加入一个常量，让加入房间、挂断、信令发送都使用同一个值，避免页面显示和实际行为不一致。

以后如果要支持多设备多房间，再给 `contract_machine` 增加 `room_id` 字段；这次先不做。

## 健康数据模拟脚本

新增一个仓库内 Python 脚本。

默认行为：

- 后端地址：`http://127.0.0.1:8080`
- 设备号：`WALLE_1`
- 发送间隔：`1.0` 秒
- 持续循环，直到手动停止

支持参数：

- `--base-url`
- `--device-id`
- `--interval`
- `--once`

每轮发送：

- 心率：默认 65 到 95 左右的真实范围
- 湿度：合理范围内的整数或小数
- 呼吸：默认 14 到 22 左右
- 体温：默认 36.2 到 37.2 左右
- 跌倒：默认大多数为 `false`，可低概率出现 `true`

脚本每次发送后打印数据内容和 HTTP 响应状态，方便在 Windows 上演示时确认是否成功。

## 前端改动

### 设备管理

登录后设备表应能看到默认设备 `瓦力 / WALLE_1`，因为后端会返回它。

默认设备的删除按钮应隐藏或禁用。

新增设备表单保留，但占位示例改得更清楚：

- 设备名称示例：`备用机器人`
- 设备号示例：`WALLE_2`

### 健康监测

默认选中设备号 `WALLE_1`。

设备列表还在加载时，页面也要显示稳定的默认状态，不能像没有设备一样空白。

刷新频率第一版保持现状。

### 远程监控

房间号固定显示为 `0001`。

房间输入框改成只读展示或禁用输入。实现上用一个常量统一所有房间逻辑。

## 测试策略

有测试支撑的后端改动按测试优先执行。

后端测试覆盖：

- 查询设备列表时，会为当前用户创建默认设备。
- 查询设备列表时，不返回其他用户的设备。
- 删除默认设备 `WALLE_1` 会被拒绝或忽略。
- 机器人控制接口会拒绝控制不属于当前用户的设备。

模拟脚本验证：

- 对本地后端运行一次模拟脚本。
- 查询 `WALLE_1` 的健康数据接口。
- 确认健康页面或 API 响应能看到最新数据。

前端验证：

- 构建 Vue 项目。
- 登录 admin。
- 设备管理能看到 `瓦力 / WALLE_1`。
- 健康监测默认使用 `WALLE_1`。
- 远程监控显示固定房间 `0001`。

## 风险

现有后端自动化测试较少，而且还有多个接口接收前端传入的用户 ID。本次先关闭演示主链路和后台管理主链路的数据串号风险，剩余未迁移接口需要在实施结果里列清楚。

当前数据库里有的表用字符串存 `user_id`，有的表用整数存用户 ID。本次避免大规模改表结构，除非被修改接口必须调整。

如果 OneNET token 真的绑定了错误拼写 `WALEE_1`，把设备名改回 `WALLE_1` 后可能需要在 OneNET 平台重新生成 token。实施时只能指出这一点，不能猜新凭证。
